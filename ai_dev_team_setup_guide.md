# 🚀 AI Developer Team: Project Setup & Initialization Guide

This guide outlines how to bootstrap a new software project utilizing a multi-agent AI developer team (Planner, Designer, Backend, Frontend, Tester, Reviewer) orchestrated via the Claude Desktop app or Cursor.

By utilizing local filesystem access (MCP / Cursor tools), these agents pass context seamlessly by reading and writing files within your project directory, creating a continuous, automated-feeling development pipeline.

---

## 🏗️ 1. Architecture Overview

Your AI development team uses a contract-driven **orchestrator-worker** architecture:

1. **Planner Agent:** Ingests feature requests and outputs an overview (`spec.md`), split specialist specs, and shared `api_contracts.json`.
2. **Designer + Backend Agents:** Run in parallel when both are assigned — Designer writes `design_tokens.json`; Backend implements API/server code against the contract.
3. **Frontend Agent:** Builds UI against design tokens and API contracts after parallel group 1 completes.
4. **Tester Agent:** Reads the modified source code and generates tests in the project's existing test locations.
5. **Reviewer Agent:** Audits specs, contracts, source, and tests, issuing a final `PASS` or `FAIL` verdict (`review.md`).

## 📂 2. Project Directory Structure

First, initialize your project repository. Create a dedicated folder for your project and set up the following directory structure. Storing the prompts inside the repository ensures version control and portability.

```text
my-app/
├── pipeline/   # or agent-outputs/pipeline/ in the Cursor shell
│   ├── prompts/
│   │   ├── 1_planner.md
│   │   ├── 2a_designer.md
│   │   ├── 2b_backend.md
│   │   ├── 2c_frontend.md
│   │   ├── 3_tester.md
│   │   └── 4_reviewer.md
│   ├── spec.md              # Overview + Work Assignment (Planner)
│   ├── api_contracts.json   # Shared API contract (Planner)
│   ├── design_tokens.json   # Design tokens (Designer)
│   ├── specs/
│   │   ├── design_spec.md
│   │   ├── backend_spec.md
│   │   └── frontend_spec.md
│   └── review.md            # Generated by Reviewer
├── src/                     # Or your real module layout
└── tests/                   # Or your real test layout
```

For the Cursor-packaged installer, see [README.md](README.md) (`agent-outputs/pipeline/` + `.cursor/agents/`).

## 🛠️ 3. Agent System Prompts (The Setup)

Create the following markdown files in your `pipeline/prompts/` directory. You will use these as system prompts or paste them into Claude Desktop when transitioning between agents.

### `1_planner.md`
> **Role:** You are the Planner Agent (Opus tier / orchestrator). Your job is to turn vague feature requests into split technical specifications and shared contracts.
> **Task:** Decide which of designer / backend / frontend are needed. Outline exact file paths with no overlapping ownership. Do NOT write the implementation code.
> **Output:** `pipeline/spec.md` (overview + Work Assignment), `pipeline/api_contracts.json`, and the applicable files under `pipeline/specs/`.

### `2a_designer.md`
> **Role:** You are the Designer Agent (Sonnet tier).
> **Task:** Read `design_spec.md` and produce concrete UI layout rules / tokens.
> **Output:** `pipeline/design_tokens.json` only — no application source.

### `2b_backend.md`
> **Role:** You are the Backend Agent (Sonnet tier).
> **Task:** Read `backend_spec.md` and implement API routes/services matching `api_contracts.json`.
> **Output:** Backend source on owned real project paths.

### `2c_frontend.md`
> **Role:** You are the Frontend Agent (Sonnet tier).
> **Task:** Read `frontend_spec.md`, `design_tokens.json`, and `api_contracts.json`. Build UI that adheres to both.
> **Output:** Frontend source on owned real project paths.

### `3_tester.md`
> **Role:** You are the Tester Agent (Sonnet tier).
> **Task:** Review backend/frontend changes. Write comprehensive tests covering happy paths and edge cases; include cross-boundary tests when both sides are in scope.
> **Output:** Test files in the project's existing test locations.

### `4_reviewer.md`
> **Role:** You are the Reviewer Agent (Opus tier), acting as a strict, read-only gatekeeper. You cannot write or edit application code.
> **Task:** Read specs, contracts, source, and tests. Evaluate for safety, performance, logic flaws, and contract adherence.
> **Output:** Write a final evaluation to `pipeline/review.md` concluding with a strict **PASS** or **FAIL**. If FAIL, list remediation steps with the responsible specialist.

## ⚙️ 4. Execution Workflow

To run a feature through the pipeline in Claude Desktop:

1. **Ensure MCP is Active:** Make sure your `claude_desktop_config.json` allows filesystem access to this project folder.
2. **Start the Planner:** Paste `1_planner.md` with your feature request (e.g., *"Add a user login portal"*).
3. **Trigger Designer + Backend in parallel:** Once specs/contracts exist, run `2a_designer.md` and `2b_backend.md` at the same time (skip either if not assigned).
4. **Trigger Frontend:** After `design_tokens.json` exists, paste `2c_frontend.md`.
5. **Trigger Tester:** Paste `3_tester.md`.
6. **Trigger Reviewer:** Paste `4_reviewer.md`.
7. **Iterate:** If the Reviewer outputs `FAIL`, pass remediation to the named specialists, then re-test and re-review.

In Cursor, prefer `/plan` which orchestrates this automatically (including parallel Task launches).

## 🚀 5. Parallelism & Contracts

This pipeline is an **Orchestrator-Worker (Hub-and-Spoke)** architecture.

### Default DAG

1. Planner writes shared contracts + partitioned specs.
2. **Designer** and **Backend** run simultaneously.
3. **Frontend** runs after design tokens (API contracts are already available from the Planner).
4. Tester → Reviewer.

### Why contracts matter

By relying on **Contract-Driven File Buses** (`api_contracts.json`, `design_tokens.json`), specialists stay synchronized without sharing conversation history — regardless of how many agents you add later.

### Backend-only or frontend-only

The Planner should assign only the specialists required. A pure API change skips designer/frontend; a pure UI polish against an existing API can skip backend (document the existing API in `api_contracts.json`).
